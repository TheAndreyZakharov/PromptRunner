# PromptRunner — описание и план разработки

## 1. Назначение приложения

PromptRunner — лёгкое кроссплатформенное desktop-приложение для macOS и Windows, которое последовательно прогоняет вопросы из указанного репозитория через заранее настроенное AI-чат-приложение.

Приложение должно:

- читать вопросы из конкретно указанной папки с банком;
- понимать текущую структуру Markdown-файлов банка;
- использовать стабильные ID вопросов вида `RU-000001` и `EN-000001`;
- брать универсальный каркас промпта из банка;
- добавлять в промпт контекст текущей подтемы и один текущий вопрос;
- вставлять промпт в AI-чат;
- отправлять его координатным кликом;
- визуально определять, закончилась ли генерация;
- копировать готовый ответ через интерфейс AI-чата;
- проверять, что скопирован ответ именно для ожидаемого ID;
- записывать ответ напрямую в Markdown-файл банка;
- продолжать работу с последнего незавершённого ID;
- каждые заданное количество вопросов открывать новый чат;
- вести журнал прогресса, ошибок и времени работы;
- работать как самостоятельное приложение `.app` на macOS и `.exe`/инсталлятор на Windows.

Главная идея — координатный black-box-тест пользовательского сценария. В основном режиме PromptRunner не ищет элементы окна, не обращается к DOM и не использует внутренний API тестируемого AI-чата: пользователь сам задаёт небольшие экранные зоны, а приложение работает с координатами и визуальными областями.

Это проверяет AI-чат именно как экранное приложение. Координатный режим не следует трактовать как гарантию отсутствия системных признаков синтетического ввода: macOS и Windows всё равно могут применять собственные разрешения, журналы и политики безопасности.

## 2. Границы проекта

### Входит в проект

- управление мышью и клавиатурой через системный слой ввода;
- ручная разметка зон интерфейса;
- визуальный контроль состояния экрана;
- работа с системным буфером обмена;
- прямое чтение и изменение Markdown-файлов;
- восстановление после перезапуска;
- повторная попытка клика в другой точке разрешённой зоны;
- пользовательские профили для разных размеров окон, мониторов и операционных систем;
- тестовые профили с воспроизводимыми вариациями задержек и траекторий для проверки UI-устойчивости.

Вариации движения курсора допускаются как воспроизводимый тестовый профиль пользовательского интерфейса.

## 3. Что уже известно о банке вопросов

В репозитории `/Users/andrey/Documents/projects/IT-Interview-Question-Bank` уже есть необходимая структура.

Основные элементы:

```text
RU/Questions_By_Topic_RU/
    исходные вопросы по темам и подтемам

EN/Questions_By_Topic_EN/
    английские исходные вопросы

RU/Questions_with_AI_Answers_By_Topic_RU/
    готовые ответы по русским вопросам

tools/answer-generation-prompt.md
    универсальный каркас промпта

tools/internal/bank/
    существующая логика разбора, ID и сопоставления ответов
```

Формат исходного вопроса:

```markdown
- Расскажите о себе. [id: RU-000001]
```

Формат вопроса в файле ответов:

```markdown
- **Расскажите о себе.** [id: RU-000001]

*Ответ:*

Текст ответа.
```

ID является главным ключом. Нельзя определять продолжение только по номеру строки, имени файла или позиции вопроса в разделе.

Существующий банк уже разделяет исходные вопросы и ответы. PromptRunner должен сохранять эту модель: исходный банк не изменяется, а ответы записываются в `Questions_with_AI_Answers_*`.

## 4. Рекомендуемый технический стек

### Основной выбор

Рекомендуемый вариант — Rust + Tauri 2 с минимальным интерфейсом на vanilla TypeScript.

Причины:

- один основной код для macOS и Windows;
- нет встроенного Chromium, как в Electron;
- небольшая поставляемая сборка;
- умеренное потребление памяти;
- удобная упаковка в `.app` и Windows-инсталлятор;
- системные операции можно держать в Rust-части;
- простой интерфейс не требует тяжёлой UI-библиотеки.

Распределение ответственности:

```text
Rust core
├── Markdown parser
├── Question index
├── Prompt builder
├── Progress state
├── Answer writer
├── Input engine
├── Screen sampler
├── Clipboard adapter
└── Run state machine

Tauri shell
└── окно приложения и вызов команд Rust

Vanilla TypeScript UI
├── настройки
├── калибровка зон
├── старт/стоп/продолжить
├── прогресс
└── лог
```

### Кандидаты на зависимости

Перед фиксацией версий нужно проверить актуальную совместимость с целевыми версиями macOS и Windows.

- Tauri 2 — desktop shell и сборка;
- Rust stable — основная логика;
- `serde` и `serde_json` — конфигурация и прогресс;
- `arboard` — буфер обмена;
- `enigo` или аналогичный актуальный crate — координатный ввод мыши и клавиатуры;
- `xcap`/`screenshots` или аналогичный актуальный crate — снимки экрана и ROI;
- `image` — сравнение визуальных образцов;
- `rfd` — системные диалоги выбора папки;
- `pulldown-cmark` либо собственный ограниченный Markdown-парсер — только для поддерживаемого формата банка;
- `uuid` или собственный генератор ID запуска;
- `tracing`/`tracing-subscriber` — журналы;
- `thiserror`/`anyhow` — ошибки;
- `tempfile` — безопасная атомарная запись файлов.

Не нужно добавлять тяжёлые браузерные фреймворки, OCR, базы данных, Electron или полноценный компьютерный vision-пайплайн: для заданного сценария достаточно работы с размеченными областями экрана.

### Выбор input backend

`enigo` удобен как кроссплатформенный слой, но он является только абстракцией над системным вводом и не делает события физическими. Поэтому input engine должен иметь отдельный интерфейс backend-а:

```text
InputBackend
├── macOSNativeBackend — CoreGraphics / CGEvent
├── WindowsNativeBackend — Win32 SendInput
└── PortableBackend — enigo как общий fallback
```

Рекомендуемый порядок:

1. на macOS использовать нативный backend через `CGEvent`;
2. на Windows использовать нативный backend через `SendInput`;
3. `enigo` оставить как переносимый fallback или использовать там, где нативный backend не даёт нужной функции;
4. выбор backend-а фиксировать в логе запуска.

Ни один программный backend не превращает синтетическое событие в событие от физической мыши. Для PromptRunner важнее проверяемое поведение: курсор не должен телепортироваться, движение должно быть плавным, а каждый тест должен быть воспроизводимым и диагностируемым. Подключение физического HID-устройства или драйвера в проект не входит.

### Альтернативный вариант

Если после измерений Tauri/WebView окажется слишком тяжёлым, UI можно заменить на `egui/eframe`, не меняя Rust core. Это должно быть запасным решением, а не параллельной реализацией с самого начала.

## 5. Функциональные требования

### 5.1 Выбор банка

Пользователь должен иметь возможность указать путь до корня репозитория вопросов.

Пример:

```text
/Users/andrey/Documents/projects/IT-Interview-Question-Bank
```

После выбора приложение проверяет:

- существует ли папка;
- найден ли `tools/answer-generation-prompt.md`;
- существуют ли каталоги `RU/Questions_By_Topic_RU` или `EN/Questions_By_Topic_EN`;
- находятся ли Markdown-файлы вопросов;
- соответствуют ли строки вопросам ожидаемому формату;
- нет ли дубликатов ID;
- есть ли директория ответов или её можно создать;
- не изменился ли банк после создания индекса.

Путь сохраняется в пользовательских настройках, но сам банк не копируется внутрь приложения.

### 5.1.1 Ограничение языка и области доступа

В репозитории одновременно могут находиться русские и английские вопросы. PromptRunner должен иметь явный языковой allowlist, чтобы пользователь мог разрешить обработку только одного набора:

```json
{
  "allowedLanguages": ["RU"],
  "activeLanguage": "RU"
}
```

Поддерживаемые варианты:

- только `RU` — обрабатываются только вопросы с ID `RU-*`;
- только `EN` — обрабатываются только вопросы с ID `EN-*`;
- `RU` и `EN` — разрешены оба языка, но активный язык всё равно выбирается отдельно;
- пустой allowlist — запуск запрещён до явного выбора языка.

При выборе `RU` приложение:

- строит рабочую очередь только по `RU/Questions_with_AI_Answers_By_Topic_RU`;
- ищет последний заполненный ответ и следующий незавершённый ID только в `RU/Questions_with_AI_Answers_By_Topic_RU`;
- читает `RU/Questions_By_Topic_RU` только для текста вопросов и контекста текущей подтемы;
- принимает только ID с префиксом `RU-`;
- не включает английские вопросы в контекст промпта;
- не ищет и не изменяет английские файлы;
- блокирует запуск, если активный язык не входит в allowlist.

При выборе `EN` действует симметричное правило.

Проверка должна выполняться до начала обработки, а не после чтения всего банка. Для активного языка нельзя молча подменять префикс ID или смешивать вопросы разных языков в одной сессии.

На macOS при включённом App Sandbox пользователь один раз выбирает папку банка через системный диалог. Приложение сохраняет разрешение на выбранную папку, но не получает автоматический доступ ко всей файловой системе. На Windows рабочим источником является только явно выбранный каталог банка.

### 5.2 Выбор языка и области обработки

Настройки должны включать:

- разрешённые языки `RU`, `EN` или оба;
- активный язык текущей сессии;
- весь банк или выбранную тему;
- выбранную подтему;
- стартовый ID;
- режим «только вопросы без ответа»;
- максимальное количество вопросов за текущую сессию;
- количество вопросов до нового чата.

Параметр «Количество вопросов за сессию» ограничивает именно текущий запуск PromptRunner. Например, при значении `50` приложение обработает не более 50 успешно записанных вопросов, сохранит прогресс и остановится в состоянии `SESSION_LIMIT_REACHED`. При следующем нажатии «Продолжить» оно начнёт со следующего незавершённого ID.

Порядок вопросов определяется числовой частью ID, а не алфавитной сортировкой строк:

```text
RU-000009
RU-000010
RU-000011
```

### 5.2.1 Переход между подтемами

Если пользователь выбрал тему целиком или весь банк, обработка должна идти по числовому порядку подтем.

Например:

```text
3.1.1 → 3.1.2 → 3.1.3 → 3.1.4 → 3.2 → 3.3 → 3.4.1 → ... → 3.6.3
```

Правила:

- сначала обрабатываются незавершённые вопросы текущей подтемы;
- вопросы внутри подтемы сортируются по числовой части ID;
- после последнего незавершённого вопроса текущей подтемы выбирается следующая подтема по номеру заголовка;
- переход не должен возвращать программу в начало уже завершённой подтемы;
- при переходе в новую подтему контекст промпта полностью пересобирается;
- в новый контекст включается список вопросов только новой подтемы;
- текущим вопросом становится первый незавершённый вопрос новой подтемы;
- если пользователь указал стартовый ID, первая подтема определяется по этому ID, а затем обработка продолжается вперёд;
- если достигнут лимит сессии, переход к следующей подтеме не выполняется до следующего запуска.

Для одной подтемы из 150–200 вопросов итоговая схема выглядит так:

```text
подтема 3.6.1
  вопрос 1 → новый промпт с контекстом 3.6.1
  вопрос 2 → новый промпт с контекстом 3.6.1
  ...
  последний вопрос → новый промпт с контекстом 3.6.1

подтема 3.6.2
  первый незавершённый вопрос → новый промпт с контекстом 3.6.2
```

Нельзя продолжать использовать контекст предыдущей подтемы после перехода.

### 5.3 Формирование промпта

Каркас полностью читается из:

```text
tools/answer-generation-prompt.md
```

К нему добавляются:

1. список вопросов текущей подтемы или выбранного контекста;
2. точный текущий вопрос в самом низу;
3. его исходный ID.

Для каждого следующего вопроса промпт формируется заново. Если закончилась подтема и началась следующая, список контекстных вопросов также заменяется полностью: старый список не переносится в новый промпт.

Рекомендуемый итоговый формат:

```text
[полный универсальный промпт]

КОНТЕКСТ РАЗДЕЛА

- вопрос текущей подтемы [id: RU-000001]
- вопрос текущей подтемы [id: RU-000002]

ТЕКУЩИЙ ВОПРОС

- точный текст текущего вопроса [id: RU-000003]
```

Полный банк из десятков тысяч вопросов нельзя добавлять в каждый запрос. По умолчанию используется текущая подтема.

Промпт должен сохранять:

- исходную формулировку вопроса;
- пунктуацию;
- язык;
- ID;
- последовательность правил из универсального шаблона.

### 5.4 Калибровка зон интерфейса

При первой установке готовых профилей нет. Пользователь сам открывает AI-чат, фиксирует его размер и в режиме «Калибровка» последовательно размечает прямоугольные зоны:

#### Зоны действий

Зоны действий определяют места, куда PromptRunner подводит курсор и выполняет действие:

- поле ввода;
- кнопка отправки;
- кнопка копирования ответа;
- кнопка нового чата;
- необязательная кнопка подтверждения или очистки.

#### Зоны наблюдения

Зоны наблюдения определяют маленькие области экрана, в которых PromptRunner ищет визуальный признак состояния. Например, это может быть область иконки, которая показывает, идёт ли генерация или она закончилась. В них приложение ничего не нажимает.

Обязательная зона наблюдения:

- индикатор или иконка состояния генерации.

Дополнительные зоны наблюдения:

- область иконки кнопки отправки, если она меняется во время генерации;
- область кнопки копирования, если она становится доступной только после ответа;
- небольшая область ответа для контроля изменения текста;
- область нового чата для подтверждения переключения.

сам выбор должен быть такими как бы блоками которые цветом выделены чтобы видно и понятно было как что куда зона ставится, чтобы каждую зону так можно было перетащить, увеличить/умеьшить ее габариты. то есть поверх всего экрана можно такие зоны перетаскивать 

Для каждой зоны сохраняются:

```json
{
  "name": "send",
  "kind": "action",
  "purpose": "submit_prompt",
  "x": 1450,
  "y": 980,
  "width": 64,
  "height": 48,
  "coordinateSpace": "screen",
  "platform": "macos",
  "displayId": "main",
  "enabled": true
}
```

Для зоны наблюдения вместо действия сохраняются визуальные образцы и правила проверки:

```json
{
  "name": "generation_state",
  "kind": "observation",
  "purpose": "detect_generation_finished",
  "x": 1800,
  "y": 580,
  "width": 80,
  "height": 80,
  "samples": ["writing.png", "send.png", "no_prompt.png"],
  "matchMode": "roi_similarity",
  "threshold": 0.92,
  "confirmationsRequired": 2,
  "enabled": true
}
```

Профиль нельзя сохранить, пока не размечены все обязательные зоны действий и обязательная зона наблюдения генерации.

Лучше поддержать два режима координат:

- `screen` — абсолютные координаты экрана;
- `windowPreset` — координаты относительно заранее откалиброванной области окна.

С самого начала нужен контроль разрешения, масштабирования, Retina и активного дисплея. Абсолютные координаты допустимы только внутри профиля, для которого они были откалиброваны.

Каждая зона должна иметь кнопку «Проверить», которая выполняет один тестовый клик после явного подтверждения пользователя.

После завершения разметки приложение предлагает сохранить раскладку как профиль. Пользователь может:

- сохранить профиль под собственным именем;
- отказаться от сохранения и использовать зоны только до закрытия приложения;
- перезаписать существующий профиль после повторной калибровки;
- сохранить отдельные профили для macOS и Windows;
- сохранить отдельные профили для разных мониторов и разрешений.

При следующем запуске PromptRunner показывает список сохранённых профилей. Если профиль не выбран, запуск блокируется до калибровки или выбора существующей раскладки.

### 5.5 Клик внутри зоны

Клик должен происходить не обязательно в центре зоны.

Для проверки того, что зона действительно покрывает кнопку, можно использовать воспроизводимую последовательность точек:

1. центр;
2. середина каждой стороны;
3. внутренние точки около углов;
4. ограниченное количество дополнительных точек.

Порядок и seed сохраняются в логе. Это нужно для повторяемости тестов и диагностики промахов.

Если клик не дал ожидаемого состояния:

- сделать паузу;
- выбрать следующую точку в той же зоне;
- повторить не более заданного числа раз;
- после исчерпания попыток остановить выполнение и показать ошибку.

Бесконечные повторы запрещены.

### 5.5.1 Требования к движению курсора

Движение к любой зоне действия должно выполняться как реалистичное поведение курсора:

- запрещён один скачок из исходной точки в конечную, движение должно быть ОЧЕНЬ ПЛАВНЫМ;
- путь строится с учётом времени движения;
- путь не должен идти ровно из одной точки до другой, должны быть колебания и искажения в маршруте;
- между промежуточными точками используется монотонный таймер;
- скорость курсора во время движения может плавно меняться;
- после прихода в зону выдерживается короткая стабилизационная пауза;
- конечная точка всегда проверяется на попадание внутрь зоны;
- выбранные параметры движения и seed записываются в лог;
- при Stop движение немедленно прекращается.

Параметры траектории нужны для воспроизводимого тестирования пользовательского сценария и проверки устойчивости интерфейса. 

### 5.6 Ввод промпта

Для большого промпта не нужно посимвольно печатать текст. Рекомендуемый сценарий:

1. сохранить прежнее содержимое буфера обмена;
2. записать промпт в `NSPasteboard` на macOS или системный clipboard на Windows;
3. координатно кликнуть поле ввода;
4. отправить сочетание вставки `Cmd+V` на macOS или `Ctrl+V` на Windows;
5. дождаться появления текста в поле визуальным способом;
6. нажать кнопку отправки координатным событием.

Старое содержимое буфера можно восстановить после завершения операции, если это не мешает проверке результата.

### 5.7 Мониторинг окончания генерации

Так как внутренний API AI-чата не используется, нужен визуальный конечный автомат.

Базовые состояния:

```text
EMPTY
SEND_READY
SUBMITTING
WRITING
EMPTY_COMPLETE
COPYING
VALIDATING
FAILED
PAUSED
```

Для визуальной проверки пользователь размечает observation ROI — небольшую область, где меняется индикатор генерации или иконка кнопки. В этой области приложение только наблюдает за пикселями и ничего не нажимает.

В калибровке для observation ROI сохраняются три образца:

```text
writing.png      # busy: ответ генерируется
send.png         # поле содержит текст, его можно отправить
no_prompt.png   # поле ввода пустое, генерация завершена
```

На каждой проверке приложение:

1. делает снимок только нужной маленькой области;
2. сравнивает его с образцами;
3. применяет допуск различия;
4. требует подтверждение состояния на двух последовательных проверках;
5. после перехода `writing → no_prompt` продолжает работу с копированием ответа.

Проверка каждые 10–15 секунд задаётся в настройках. Дополнительно нужны:

- минимальное время ожидания после отправки;
- максимальное время одной генерации;
- количество подтверждений готового состояния;
- пауза между кликом копирования и чтением буфера;
- ручная кнопка «Считать готовым» для аварийного режима.

Если визуальные образцы не совпали, PromptRunner не должен автоматически переходить к следующему вопросу. Он обязан поставить запуск на паузу.

### 5.8 Копирование и проверка результата

Перед кликом копирования нужно записать в clipboard уникальный sentinel, чтобы отличить новый результат от старого содержимого.

После клика:

1. подождать заданный интервал;
2. прочитать буфер обмена;
3. убедиться, что sentinel исчез;
4. проверить наличие ожидаемого ID;
5. проверить первую строку Markdown;
6. проверить наличие `*Ответ:*` или `*Answer:*`;
7. проверить, что ответ не пустой;
8. при ошибке не переходить дальше.

Минимальная проверка ID:

```text
ожидается: RU-004898
найдено в первой строке: RU-004898
результат: OK
```

Если AI-чат скопировал только часть ответа или старый ответ, вопрос остаётся незавершённым.

### 5.9 Запись ответа в Markdown

Запись должна повторять фактический формат файлов вопросов с ответами в банке.

В файле ответов незаполненный вопрос представлен строкой вида:

```markdown
- Как работает SSL stripping-атака? [id: RU-004956]
```

После успешного копирования AI-ответа эта строка целиком заменяется содержимым clipboard. Clipboard уже содержит готовый блок с точным вопросом, ID, меткой `*Ответ:*` и текстом ответа:

```markdown
- **Как работает SSL stripping-атака?** [id: RU-004956]
*Ответ:*

Текст ответа.
```

После вставленного блока добавляются два пропуска строк по принятому формату банка, чтобы следующий вопрос начинался с нужным разделителем. Реализация должна нормализовать завершающие переводы строк и явно тестировать ожидаемый результат, чтобы не получить лишние или недостающие пустые строки.

Исходный каталог вопросов не изменяется.

Ответ записывается в соответствующий файл внутри:

```text
RU/Questions_with_AI_Answers_By_Topic_RU/
EN/Questions_with_AI_Answers_By_Topic_EN/
```

Алгоритм:

1. определить файл по теме и подтеме вопроса внутри `Questions_with_AI_Answers_By_Topic_*`;
2. найти строку незаполненного вопроса по ожидаемому ID;
3. не доверять только позиции строки — проверить текст и ID;
4. заменить найденную строку полным содержимым clipboard;
5. нормализовать конец clipboard-блока и добавить два пропуска строк по формату банка;
6. если по ID уже существует готовый блок — не создавать дубликат;
7. сохранить исходные line ending и кодировку;
8. записать новый файл во временный путь;
9. проверить, что временный файл читается и содержит ровно один блок нужного ID;
10. атомарно заменить целевой файл;
11. повторно перечитать целевой файл;
12. обновить progress state только после успешной записи.

Для реализации нужен отдельный helper, например `replaceQuestionLineWithAnswerBlock`, и fixture-тест:

```text
вход:  вопрос без ответа + следующий вопрос
выход: полный clipboard-блок + два пропуска строк + следующий вопрос
```

Таким образом, PromptRunner не должен имитировать ввод текста в редакторе или двигать мышью по VS Code. Он непосредственно изменяет нужный Markdown-файл, а мышь используется только для взаимодействия с тестируемым AI-чатом.

Нельзя отмечать вопрос завершённым только после получения текста в буфере. Завершение фиксируется после успешной записи на диск.

### 5.10 Новый чат каждые N вопросов

По умолчанию:

```text
newChatEvery = 100
```

После каждого сотого успешно записанного ответа:

1. завершить текущую операцию;
2. подождать указанную паузу;
3. выполнить настроенное действие нового чата;
4. визуально проверить, что появился пустой чат;
5. только после этого продолжить.

Предлагаемые действия:

- macOS: `Cmd+N`, если это поддерживается конкретным AI-приложением;
- Windows: `Ctrl+N`, если это поддерживается конкретным AI-приложением;
- координатный клик по кнопке «Новый чат»;
- отдельная зона нового чата в пресете.

Сочетания клавиш не универсальны: в некоторых приложениях они создают новое окно, а не новый чат. Поэтому действие должно быть частью target preset и проходить визуальную проверку.

## 6. Профили и пресеты

В пользовательском интерфейсе используется термин «профиль». Внутри программы профиль объединяет координаты, визуальные образцы и платформенные настройки.

В репозитории по умолчанию нет готовых профилей. Первый профиль появляется только после ручной калибровки пользователем и явного подтверждения «Сохранить профиль».

Жизненный цикл профиля:

1. пользователь запускает PromptRunner без профилей;
2. открывает режим калибровки;
3. размечает поле ввода, отправку, состояние генерации, копирование и новый чат;
4. проверяет зоны тестовыми действиями;
5. задаёт имя в окне калибровки и нажимает «Сохранить»;
6. PromptRunner атомарно сохраняет или обновляет профиль на диске и выбирает его для следующих запусков;
7. при следующем запуске выбирает его из списка.

При отмене калибровки изменения не сохраняются. После успешного «Сохранить» профиль остаётся на диске, а повторная калибровка существующего профиля обновляет его по тому же ID, не создавая потерянную временную копию.

Пример структуры:

```json
{
  "name": "My AI Chat — macOS 2560x1440",
  "platform": "macos",
  "display": {
    "width": 2560,
    "height": 1440,
    "scale": 2.0
  },
  "zones": {
    "input": { "x": 1000, "y": 920, "width": 850, "height": 90 },
    "send": { "x": 1830, "y": 940, "width": 70, "height": 60 },
    "generationState": { "x": 1800, "y": 580, "width": 80, "height": 80 },
    "copy": { "x": 1870, "y": 580, "width": 70, "height": 70 },
    "newChat": { "x": 230, "y": 100, "width": 120, "height": 50 }
  },
  "shortcuts": {
    "paste": "cmd+v",
    "newChat": "cmd+n"
  },
  "visual": {
    "pollIntervalSeconds": 10,
    "readyConfirmations": 2,
    "generationTimeoutSeconds": 900
  }
}
```

Файлы пресетов не должны содержать содержимое вопросов, ответы или секреты.

## 7. Progress state и восстановление

Прогресс хранится отдельно от Markdown.

Пример:

```json
{
  "runId": "2026-08-29T12:00:00Z-abc123",
  "bankPath": "/path/to/IT-Interview-Question-Bank",
  "bankFingerprint": "sha256:...",
  "allowedLanguages": ["RU"],
  "activeLanguage": "RU",
  "scope": "3.6.3",
  "sessionQuestionLimit": 100,
  "sessionProcessedCount": 13,
  "startId": "RU-004898",
  "lastCompletedId": "RU-004910",
  "currentId": "RU-004911",
  "currentSection": "3.6.3",
  "lastCompletedSection": "3.6.3",
  "processedCount": 13,
  "failedIds": [],
  "chatBatchCount": 13,
  "startedAt": "2026-08-29T12:00:00Z",
  "updatedAt": "2026-08-29T15:30:00Z"
}
```

Правило восстановления:

- если ответ уже присутствует и проходит проверку ID — вопрос считается завершённым;
- если приложение остановилось до записи — вопрос повторяется;
- если запись прошла, но приложение упало до обновления JSON — повторно проверяется Markdown по ID;
- если банк изменился, запуск блокируется до явного подтверждения пользователя;
- во время запуска запрещается автоматический reindex ID;
- если достигнут `sessionQuestionLimit`, прогресс сохраняется, а запуск корректно останавливается;
- при продолжении выбор следующего вопроса выполняется по ID и числовому порядку подтем;
- при переходе между подтемами обновляется `currentSection` и пересобирается контекст промпта.

`lastCompletedId` — удобный указатель, но источником истины остаются существующие ответы и список завершённых ID.

## 8. Интерфейс приложения

Интерфейс должен быть функциональным и лёгким, без сложного CSS.

### Главный экран

- путь к репозиторию;
- разрешённые языки;
- активный язык текущей сессии;
- выбранный пресет;
- выбранная тема/подтема;
- стартовый ID;
- количество вопросов за текущую сессию;
- количество вопросов уже выполнено в текущей сессии;
- найденное количество вопросов;
- количество уже готовых ответов;
- кнопки `Старт`, `Пауза`, `Продолжить`, `Стоп`;
- текущий ID;
- время работы;
- компактный лог.

### Прогресс

Прогресс отображается отдельными полосами с количеством выполненных вопросов и процентом:

- текущий большой пункт: выполнено из общего количества вопросов пункта;
- текущий подпункт: выполнено из общего количества вопросов подпункта;
- весь банк активного языка: выполнено из общего количества вопросов;
- количество вопросов текущей сессии при этом остаётся отдельным числовым показателем рядом с текущим ID.

После каждого успешно записанного ответа значения обновляются. При переходе к следующему пункту или подпункту соответствующие текущие полосы переключаются автоматически.

### Настройки

- разрешить обработку только `RU`, только `EN` или обоих языков;
- выбрать активный язык из разрешённых;
- интервал проверки, по умолчанию 10 секунд;
- минимальная пауза между запросами, по умолчанию 10–15 секунд;
- таймаут генерации;
- число подтверждений готового состояния;
- число повторных кликов в зоне;
- число вопросов до нового чата;
- режим сохранения старого буфера;
- выбор пресета;
- режим темы: светлая, тёмная, системная.

### Экран калибровки

- инструкция по текущей зоне;
- кнопка `Записать зону`;
- отображение прямоугольника;
- тестовый клик;
- повторная калибровка;
- сохранение образцов `writing/busy`, `send` и `no_prompt`;
- проверка всех зон одним тестовым прогоном.

### Лог

Каждая строка должна содержать:

- время;
- уровень `INFO`, `WARN`, `ERROR`;
- ID вопроса;
- действие;
- длительность;
- краткое описание результата.

Пример:

```text
12:04:10 INFO  RU-004898 prompt_built context=3.6.3
12:04:12 INFO  RU-004898 submitted
12:04:22 INFO  RU-004898 generation_check state=GENERATING
12:05:02 INFO  RU-004898 generation_check state=EMPTY_COMPLETE
12:05:04 INFO  RU-004898 clipboard_validated
12:05:05 INFO  RU-004898 answer_written
```

## 9. Архитектура выполнения

```text
QuestionBank
    ↓
QuestionIndex
    ↓
ProgressResolver
    ↓
PromptBuilder
    ↓
CoordinateInput
    ↓
VisualStateMonitor
    ↓
ClipboardReader
    ↓
AnswerValidator
    ↓
AtomicAnswerWriter
    ↓
ProgressStore
    ↓
следующий ID
```

Состояния основной машины:

```text
Idle
  → ValidatingConfig
  → LoadingBank
  → SelectingNextQuestion
  → BuildingPrompt
  → PreparingClipboard
  → FocusingInput
  → PastingPrompt
  → VerifyingPromptPresence
  → Submitting
  → WaitingForGeneration
  → CopyingAnswer
  → ValidatingAnswer
  → WritingAnswer
  → UpdatingProgress
  → MaybeStartingNewChat
  → SelectingNextQuestion
```

Любая ошибка переводит запуск в `Paused` или `NeedsReview`, а не сразу к следующему ID.

## 11. Негативные и аварийные сценарии

PromptRunner должен останавливаться, а не продолжать вслепую, если:

- не найдено поле ввода по калиброванной зоне;
- окно AI-чата закрыто;
- активен другой монитор или изменилось разрешение;
- визуальное состояние неоднозначно;
- генерация превысила таймаут;
- clipboard не изменился после копирования;
- ID ответа не совпадает с текущим ID;
- ответ пустой или обрезан;
- Markdown-файл нельзя записать;
- банк изменился во время запуска;
- команда нового чата не дала ожидаемого состояния;
- пользователь начал взаимодействовать с окном во время критической операции;
- приложение потеряло разрешение на ввод или захват экрана.

Во всех таких случаях нужно сохранять:

- текущий ID;
- последнюю завершённую фазу;
- выбранную координату;
- снимок диагностической ROI, если разрешено настройками;
- текст ошибки;
- время ошибки;
- номер попытки.

## 14. Итоговая архитектурная рекомендация

Разработка должна идти сквозными проверяемыми этапами: после каждой подсистемы выполняются её unit-, integration- и end-to-end-тесты, но все требования целевого релиза закладываются в архитектуру сразу.

Полный рабочий цикл выглядит так:

```text
прочитать банк
→ применить allowlist языка
→ определить следующую подтему и незакрытый ID
→ сформировать контекст именно этой подтемы
→ вставить промпт
→ плавно подвести курсор к зоне отправки
→ отправить
→ визуально дождаться готовности
→ скопировать
→ проверить ID и формат
→ заменить строку вопроса clipboard-блоком
→ добавить два пропуска строк
→ сохранить прогресс
→ перейти к следующему ID или следующей подтеме
```

До упаковки должны быть проверены полный сценарий, переходы между подтемами по 150–200 вопросов, лимит сессии, новый чат, восстановление после сбоев, RU/EN-ограничения, macOS и Windows, а также размер и потребление ресурсов.
